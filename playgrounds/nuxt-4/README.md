# Nuxt 4 playground

The mid-level form of `unauth/n` on Nuxt v4.6: one route file per provider with its options inline, and a session util that knows nothing about sign-in. Nuxt v4.6 still runs on Nitro v2 and h3 v1, but a handler defined through `defineEventHandler` from `nuxt/server` receives the web-standard `RequestEvent` (`{ req, res, context }`), which `unauth/n` and `unjwt/session` take as it is. Nuxt auto-imports what `server/utils/` exports, so routes use `useAuthSession` and `atproto` without an import; the helpers come from `nuxt/server`, explicitly.

```sh
pnpm dev:prepare # at the repository root, once: the stub dist runs from src; `pnpm build` works too
pnpm dev:nuxt    # at the repository root, or `pnpm dev` here; a dev appSecret is generated into .nuxt/app-secret

NUXT_APP_SECRET=$(openssl rand -base64 32) pnpm build && pnpm start
```

## Files

- [`nuxt.config.ts`](./nuxt.config.ts): the runtime config. `github` holds the OAuth app (`NUXT_GITHUB_CLIENT_ID`, `NUXT_GITHUB_CLIENT_SECRET`), `public.origin` is where the app is reached (`NUXT_PUBLIC_ORIGIN`). See [`.env.example`](./.env.example).
- [`shared/types/session.d.ts`](./shared/types/session.d.ts): `SessionData`, which extends `AuthSessionData`, what a sign-in writes. Nuxt makes it visible to the utils and the routes.
- [`server/utils/session.ts`](./server/utils/session.ts): the session alone. One `defineJWESession` with `maxAge: "1h"` and `rolling: "15m"`, keyed from Nuxt's own `appSecret` (`NUXT_APP_SECRET`, generated by `nuxt dev`, required by a build): `deriveSecret("unauth:session")` returns 32 HKDF bytes, turned into an `A256GCM` `oct` JWK. `deriveSecret` needs the runtime config, so the definition is created on the first call, not at module load. `useAuthSession(event)` and `requireAuthSession(event)`, which answers `401` through `createError` before sign-in. They take `WebSessionEvent`, not only Nuxt's event, so the WebSocket upgrade can use them too.
- [`server/routes/auth/github.get.ts`](./server/routes/auth/github.get.ts): both legs of the GitHub sign-in on one route, `defineGitHubHandler` with the provider's options and the sign-in's side by side. The callback is this route on `origin`; register it at GitHub as `http://localhost:3000/auth/github`. The handler is wrapped in `defineEventHandler` from `nuxt/server`: a plain `(event) => …` default export is handed the raw h3 v1 event, whose `req` is Node's `IncomingMessage`. The flow key is Nuxt's own derived secret for the purpose `unauth:flow`: the `key` callback turns `deriveSecret("unauth:flow")`'s 32 bytes into an `A256GCM` `oct` JWK, as the session util does for `unauth:session`, with no second derivation; it runs on the first request, when the runtime config is there, and its key is kept.
- [`server/utils/atproto.ts`](./server/utils/atproto.ts): the AT Protocol provider, defined once because two routes need it. Its identity is `/oauth-client-metadata.json` on `origin`; under `nuxt dev` that is a `localhost` URL no server can fetch, so the provider uses the spec's development client, and `devHosts: ["localhost"]` moves a start on `localhost` to `127.0.0.1`, the loopback callback the atproto profile requires, then hands the result back to `localhost`.
- [`server/routes/auth/atproto.get.ts`](./server/routes/auth/atproto.get.ts): `defineAtprotoHandler` on that provider, wrapped and keyed the same way. `GET /auth/atproto?login=<handle, DID or server URL>` starts; the handler reads `login` from the query.
- [`server/routes/oauth-client-metadata.json.get.ts`](./server/routes/oauth-client-metadata.json.get.ts): the provider's `client.metadata`, the document published at its `clientId`; it is absent for the development client, so the route answers nothing there.
- [`server/routes/login.post.ts`](./server/routes/login.post.ts): a password login without a password, for trying the session: it clears the session and writes `{ provider: "password", subject, signedInAt }`, the replace-then-write a sign-in does.
- [`server/routes/me.get.ts`](./server/routes/me.get.ts): the protected route, through `requireAuthSession`. [`logout.post.ts`](./server/routes/logout.post.ts) clears the session.
- [`server/routes/ws.ts`](./server/routes/ws.ts): a WebSocket at `/ws`. The session is read once, in `upgrade`, the only hook that can refuse; what the socket needs is copied onto `request.context`, which every later hook receives as `peer.context`, and the headers `upgrade` returns ride on the `101`, so a roll or an expired cookie's deletion reaches the browser. `defineWebSocketHandler` is the one `h3` import: `nuxt/server` has no WebSocket API yet.
- [`server/routes/throw-after-clear.get.ts`](./server/routes/throw-after-clear.get.ts): clears, then throws a `401`. On Nitro v2 the `Set-Cookie` written before the throw stays on the Node response, so the error response signs the client out too.
- [`app.vue`](./app.vue): one button per route and a log of what each answered.

## Handlers come from `nuxt/server`

Nuxt's auto-imported `defineEventHandler` is still h3's, and its handler receives the raw h3 v1 event, as does a plain function exported as it is. The session refuses that event, and so do the session helpers of `nuxt/server`:

```text
[unjwt/session] use() got an event whose "req" is not a web Request.
```

So every HTTP route takes `defineEventHandler` from `nuxt/server`, and with it `readBody`, `createError` and `useRuntimeConfig`: the code stays on the surface Nuxt keeps portable across its server runtimes. `createError` is what Nitro v3's `HTTPError` is in the Nitro playground.

## Type checking

`pnpm typecheck` here runs `nuxt typecheck`, which is `vue-tsc` on TypeScript 6 against the project references Nuxt generates into `.nuxt/`, so `pnpm dev:prepare` (or `nuxt prepare`) comes first.
